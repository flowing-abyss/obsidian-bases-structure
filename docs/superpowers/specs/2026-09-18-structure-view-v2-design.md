# Structure View v2 — диагностика, операции, стабильный рендеринг

Продолжение спецификации `2026-09-15-structure-view-design.md`. Всё, что там описано, остаётся в силе;
здесь только новое поведение. Конфигурация по-прежнему живёт в `.base`, новых ключей схемы этот
документ не вводит.

## 1. Диагностика неправильных связей

Плагин рисует иерархию по свойствам-ссылкам, поэтому пользователь легко создаёт связь, которую схема
не допускает. Такие места нужно показывать прямо на графе, а не прятать.

### 1.1 Модель

Новый чистый модуль `src/core/diagnostics.ts`:

```ts
export type DiagnosticKind = 'illegal-parent' | 'broken-link' | 'untyped' | 'inherit-mismatch';

export interface Diagnostic {
  readonly kind: DiagnosticKind;
  readonly node: string; // путь заметки, к которой относится проблема
  readonly target?: string; // вторая сторона связи (путь или сырой текст ссылки)
  readonly property?: string; // ключ frontmatter, где живёт проблема
  readonly keys?: readonly string[]; // для 'inherit-mismatch' — расходящиеся ключи
  readonly message: string; // готовая фраза для подсказки, без префикса «Structure:»
}

export function collectDiagnostics(
  schema: Schema,
  snapshot: Snapshot,
  structure: Structure,
): readonly Diagnostic[];
```

Функция чистая, без импортов Obsidian, и вызывается там же, где строится структура.

### 1.2 Что считается проблемой

1. `illegal-parent` — значение свойства, которое схема использует как связь (правая часть `children`
   или элемент `inherit`), ссылается на заметку из базы, чей тип не может быть родителем по этому
   свойству для типа этой заметки. Пример: `category: [[какая-то проблема]]`.
2. `broken-link` — значение такого свойства не разрешается ни в один файл.
3. `untyped` — заметка попала в результаты базы, но не подошла ни под один тип, и в схеме нет
   типа-перехватчика (`{}`).
4. `inherit-mismatch` — у заметки есть первичный родитель, и по ключу из `inherit` её значение не
   совпадает со значением, которое даёт этот родитель (та же величина, которую считает
   `deriveSubtreeWrites` при перемещении). Ключ, которого у родителя нет и у ребёнка нет, проблемой
   не считается; лишнее значение у ребёнка — считается.

Проблемы вычисляются для всех узлов структуры, включая сирот. Корень проверяется только по 1–3.

### 1.3 Отображение

- `illegal-parent` и `broken-link` рисуются как **красная пунктирная связь** от заметки к цели со
  значком ✕ в середине. Если цель не входит в граф (битая ссылка или заметка вне базы), связь
  выходит из узла коротким «обрывом» с тем же значком, без второго узла.
- `untyped` — значок ✕ у названия узла.
- `inherit-mismatch` — **янтарная точечная** связь до первичного родителя и маленький значок у
  названия.
- Во всех случаях значок несёт `title` с текстом `Diagnostic.message`; в outline вместо связей
  показываются те же значки у строки, текст — в `title`.
- Диагностика включена всегда, отдельной настройки вида нет.
- Цвета берём из переменных темы (`--text-error`, `--text-warning`), собственных значений не вводим.

### 1.4 Действие «Fix inheritance»

Для узла с `inherit-mismatch` в меню появляется пункт «Fix inheritance». Он планируется как обычное
действие: `{ kind: 'fix-inherit', node }` → план с записями наследуемых ключей узла и его поддерева,
та же проверка симуляцией, та же отмена. Никаких новых путей записи.

## 2. Матрица операций

### 2.1 Принцип

Цель подсвечивается только тогда, когда операция целиком допустима: заметка, её поддерево и
наследуемые свойства после операции остаются валидными по схеме. Недопустимое не подсвечивается и
не выполняется; при попытке — сообщение с конкретной причиной.

### 2.2 Обычное перетаскивание — перемещение

Как сейчас, но с одним изменением: связь-правило между типом цели и типом заметки может быть не
только свойством, но и текстовой ссылкой (`file.backlinks`, `file.links`). Набор целей по-прежнему
даёт планировщик (`moveTargets`), а не вид.

### 2.3 Текстовые связи становятся записываемыми

Для правила `file.backlinks` (родитель упоминает ребёнка в тексте):

- **Добавление** — в конец заметки нового родителя дописывается строка `- [[Имя]]` (существующий
  механизм `Plan.appends`).
- **Удаление** — из текста старого родителя убирается упоминание ребёнка. Разбор идёт **по самой
  ссылке, а не по формату строки**: работает и `- [[Имя]]`, и `* [[Имя|алиас]]`, и просто
  упоминание внутри абзаца. Удаляется только сама ссылка; если после этого строка состоит лишь из
  маркера списка и пробелов, удаляется вся строка.
- **Встраивания (`![[Имя]]`) не трогаются.** Если единственное упоминание — встраивание, операция
  отклоняется с сообщением, что ссылка на ребёнка встроена в текст и её нужно поправить вручную.
- Правило `file.links` (ребёнок упоминает родителя) работает симметрично: строка дописывается и
  удаляется в заметке ребёнка.

В `Plan` добавляется поле `bodyLinkRemovals: ReadonlyArray<{ path, target }>`, в транзакции — шаг
`bodyEdit` с точным удалённым текстом и его смещением. Отмена возвращает текст на прежнее место, а
если соседний текст изменился — дописывает строку в конец и сообщает об этом в уведомлении о
частичной отмене (тот же формат, что и у пропущенных заметок сейчас).

### 2.4 Shift + перетаскивание — преобразование

Новое действие `{ kind: 'convert', node, parent, type }` — перемещение вместе со сменой типа, один
план и одна запись отмены.

- Цели при зажатом Shift: родители, под которыми существует хотя бы один тип `T`, такой что заметку
  можно перевести в `T` (рецепт типа записываем: тег, папка или свойство), связь `T` под целью
  существует, и **всё поддерево остаётся валидным** — для каждого ребёнка `C` заметки должна
  существовать связь между `T` и типом `C`, а наследуемые ключи пересчитываются на всю глубину.
- При отпускании: один подходящий `T` — выполняем сразу; несколько — меню под курсором с именами
  типов; Escape отменяет.
- Отклонение объясняет причину и называет мешающих потомков (первого из них), как сейчас делает
  проверка перемещения.
- Обычное перетаскивание никогда не меняет тип; Shift никогда не выполняет операцию, которая
  разрушит ветку.

### 2.5 Симметричность

Правила читаются из схемы в обе стороны: если `A` можно превратить в `B` и перенести под цель, то и
обратная операция допустима ровно при тех же условиях (существует рецепт типа и связь, поддерево
валидно). Отдельных исключений в коде нет — допустимость всегда считается одной функцией
`operationTargets(schema, structure, node, mode)`, где `mode` = `'move' | 'convert'`.

### 2.6 Ветка следует за узлом

Перемещение и преобразование всегда переносят **всё поддерево**: дети продолжают ссылаться на
перемещённую заметку (через свойство или через её текст), а наследуемые ключи пересчитываются на
всю глубину, а не только у самого узла. Ни одна операция не должна оставлять потомка под старым
родителем или с наследуемыми значениями прежней ветки. Это проверяется и симуляцией плана (после
операции у каждого потомка тот же родитель, что и до неё), и живой проверкой на ветке глубиной не
меньше трёх уровней.

## 3. Стабильный рендеринг

### 3.1 Сверка вместо перестройки

Оба рендерера перестают пересоздавать все элементы на каждое обновление:

- элементы узлов хранятся по пути; существующий узел обновляется на месте (название, классы,
  значки, диагностика), новый создаётся, исчезнувший удаляется;
- порядок в outline и позиции в графе назначаются после сверки;
- перенос состояния Supercharged Links между рендерами (`previousTitle`) остаётся только для
  действительно новых элементов.

### 3.2 Оптимистичное применение

После создания, перемещения, преобразования и «Fix inheritance» вид сразу показывает результат,
который уже посчитала симуляция плана (`applyPlan`), не дожидаясь повторного запроса Bases. Когда
приходят настоящие данные, сверка тихо приводит картинку к ним. Если операция провалилась,
оптимистичное состояние отбрасывается и показывается прежнее.

### 3.3 Прокрутка

Прокрутка и масштаб не сбрасываются при обновлении данных (как сейчас), а при изменении раскладки
положение активного узла в окне сохраняется: после сверки прокрутка компенсируется на величину
сдвига этого узла.

## 4. Иконки Supercharged Links

Supercharged Links дописывает иконку после ссылки асинхронно, уже после того, как узел измерен,
поэтому иконка уезжает на новую строку, под которую в коробке нет высоты, и узлы наезжают друг на
друга.

Решение: после правок Supercharged Links (мы уже подключены к нему через
`hookSuperchargedLinks`) вид пересчитывает размеры и позиции узлов — без перестройки DOM, с
задержкой в один кадр и объединением подряд идущих правок. Коробка вырастает под иконку, наложение
исчезает. Если плагин не установлен, ничего не происходит.

## 5. Контекстное меню

Правый клик по названию узла собирает `Menu`, наполняет его нативными пунктами ссылки
(`app.workspace.trigger('file-menu', menu, file, 'link-context-menu')` — так в меню попадают и
пункты Obsidian, и пункты других плагинов), затем добавляет разделитель и операции структуры:
«Add child», «Move to…», «Change type», «Fix inheritance» (только при расхождении). Кнопка меню на
узле показывает то же самое меню. Клавиатурные сочетания не меняются.

## 6. Границы

Сознательно не делаем:

- массовое исправление всех проблем одной кнопкой — только по узлу;
- перетаскивание нескольких узлов сразу;
- правку встраиваний (`![[…]]`) и содержимого заметок за пределами одной строки со ссылкой;
- новые ключи схемы и новые настройки вида;
- анимации перестроения — стабильность достигается сверкой, а не переходами;
- режим прототипирования (черновик и панель-буфер) — он остаётся следующим этапом.

## 7. Проверка

- Модульные тесты: `diagnostics` на каждый вид проблемы и на отсутствие ложных срабатываний;
  планирование `convert` и перемещения по текстовым ссылкам, включая отказ при встраивании;
  удаление упоминания в разных форматах строки; отмена правки текста, в том числе с конфликтом;
  сверка рендереров (узел не пересоздаётся, прокрутка сохраняется, оптимистичное состояние
  заменяется настоящими данными); меню содержит нативные и наши пункты.
- Живая проверка в `dev-vault-structure` на схеме пользователя и на демо-схемах: диагностика на
  специально испорченных заметках, перетаскивание иерархии на иерархию, Shift-преобразование
  проблемы в мета-заметку, отсутствие мигания при создании, иконки Supercharged Links, контекстное
  меню. Каталог `dev-vault-structure/base/` не изменяем — для порчи данных используем `demos/`.

## 8. Известные отложенные мелочи

Найдены ревью и сознательно оставлены — ни одна не мешает пользоваться видом:

- Крестики ошибок у соседних узлов оказываются рядом, когда цель ошибочной ссылки не нарисована:
  обрывки связей выходят из узлов почти в одной точке.
- Подсветка целей при обычном перетаскивании проверяет схему, а при Shift — строит полный план.
  Поэтому обычное перетаскивание изредка подсвечивает цель, которую планировщик потом отклонит с
  объяснением.
- Прокрутка сохраняет положение активного узла только в графе; в outline восстанавливается прежняя
  позиция прокрутки.
- Диагностика `illegal-parent` может ложно срабатывать на ссылку за пределы базы, если два типа
  претендуют на один дочерний тип через разные свойства.
- Для текстовой связи вида `file.links`, чей ключ одновременно наследуемый и является свойством
  связи родителя, планировщик может не удалить упоминание: проверка смотрит на состояние до плана.
  Заметка остаётся упомянутой и рисуется дополнительной пунктирной связью.
- `requestAnimationFrame` в графе берётся из глобального окна, а не из окна вида: в отдельном окне
  Obsidian пересчёт раскладки привязан к часам главного окна.
- Пустой граф не сбрасывает запомненную раскладку, поэтому первый непустой рендер после него может
  один раз дёрнуть прокрутку.

## 9. Уточнения после разбора 2026-09-18 (v3)

- Нарушение показывается на самой ссылке: значение свойства схемы, которое не является ни допустимой
  связью по типам, ни оправданной наследуемой копией, помечается красным. Янтарным остаётся только
  расхождение по ключу, который этот тип в принципе может наследовать по схеме, — поэтому сломанный
  родитель больше не красит своего нормального ребёнка.
- Смена типа всегда требует подтверждения, даже когда подходящий тип один; пункт меню называет
  результат: «Make "<имя>" a <Тип> here».
- Преобразование запрещено, если после него у заметки появятся новые дети (случай связи по тексту);
  в отказе названа первая заметка, которая была бы «усыновлена».
- При перетаскивании подсвечивается вся ветка, которая переедет вместе с узлом.
- Плагин пишет только то, что описано в схеме: тег типа, свойства-связи из `children`/`inherit` и
  папку типа с `folder`. Прочие теги, `icon`, `color`, `aliases`, описание и текст заметки не
  трогаются — это закреплено тестами.
- Отложено: если в схеме два разных типа-родителя используют одно и то же имя свойства для разных
  дочерних типов, недопустимая ссылка покажется янтарной, а не красной.
