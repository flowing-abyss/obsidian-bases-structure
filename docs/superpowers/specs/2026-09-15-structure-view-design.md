# Structure View — дизайн

Новый тип вида для Bases: рисует иерархию заметок и позволяет достраивать её прямо на графе.
Первый сценарий — хранилище `Base/Obsidian` (Category → Meta-note → Problem → Hierarchy), но схема
описывает любую иерархию на свойствах-ссылках, тегах, папках и ссылках в тексте.

## Цели и границы

Первая версия:

- граф от одного корня, визуально не хуже прежнего mermaid-скрипта `templates/views/structure/view.js`;
- второе представление — outline (дерево-список);
- «+» на узле: выбрать допустимый тип, ввести имя, заметка создаётся со всеми связями;
- перенос узла перетаскиванием и через «Переместить в…» с каскадным обновлением потомков;
- смена типа узла;
- отмена любого из этих действий.

Позже, на том же ядре: режим прототипа (черновик + буфер + «Сохранить»).

Не делаем: свой язык запросов и формул, правку существующего текста заметок, оформление (иконки,
цвета — зона другого плагина), хранение масштаба/позиции в `.base`.

## Конфиг вида

Всё хранится в записи вида в `.base`. Obsidian переписывает эту запись целиком при любой правке
(комментарии пропадают, `[a, b]` становится блочным списком), поэтому ключи должны читаться без
комментариев.

```yaml
- type: structure
  name: 📋 Structure
  inherit:
    - category
    - meta
    - problem
  types:
    Category:
      tag: system/category
      children:
        Meta-note: category
        Hierarchy: category
    Meta-note:
      tag: system/high/meta
      children:
        Problem: meta
        Hierarchy: meta
    Problem:
      tag: system/high/problem
      children:
        Hierarchy: problem
    Hierarchy:
      tag: system/high/hierarchy
      children:
        Hierarchy: file.backlinks
```

Минимальный конфиг без типов — одна строка `parent: up`.

### Ключи

| Ключ                   | Значение                                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------------- |
| `parent`               | свойство ребёнка со ссылкой на родителя по умолчанию (для режима без типов и `children: [..]`) |
| `inherit`              | свойства-ссылки, которые потомки копируют у предков                                            |
| `types.<Имя>`          | тип с произвольным именем; порядок типов сверху вниз = уровни                                  |
| `types.<Имя>.tag`      | тег (строка или список); вложенные теги подходят                                               |
| `types.<Имя>.folder`   | папка (с подпапками)                                                                           |
| `types.<Имя>.property` | `имя: значение`; для списка — «содержит»                                                       |
| `types.<Имя>.children` | `Тип ребёнка: свойство` или список типов (свойство = `parent`)                                 |
| `layout`               | `graph` (по умолчанию) или `outline`                                                           |

Правило для `children`: справа — свойство ребёнка, в котором лежит родитель. `note.` в имени
свойства допускается и отбрасывается. Особые значения из словаря Bases:

- `file.backlinks` — родитель ссылается на ребёнка (в тексте или где угодно);
- `file.links` — ребёнок ссылается на родителя.

`file.*` при переносе не записывается (правка чужого текста). При создании ссылка дописывается:
для `file.backlinks` строкой `- [[Новая]]` в конец родителя, для `file.links` — в текст новой заметки.

### Опознание типа

- Условия внутри типа объединяются через «И». Тип без условий (`{}`) — все остальные заметки.
- Если подходят несколько типов, выигрывает тип с большим числом условий; при равенстве — первый по
  порядку и предупреждение «конфликт типов».
- Условия проверяет плагин по кешу метаданных, поэтому тип известен у любой заметки, включая корень
  вне фильтра.
- Эти же условия — рецепт записи: при создании и смене типа ставится тег, пишутся свойства, заметка
  кладётся/переносится в папку. Для смены типа снимаются теги и значения свойств старого типа.

Заметки из результатов Bases, не подошедшие ни под один тип, в граф не попадают.

### Ошибки конфига

Неизвестный тип в `children`, пустое свойство, неверные значения — вид показывает список проблем
над графом и строит то, что может.

## Построение дерева

Входы: записи Bases (уже отфильтрованы и отсортированы), корень, схема.

**Корень.** Если вид встроен в заметку и эта заметка подходит под тип (или на неё указывает хоть одна
связь) — она корень. Иначе (`.base` открыт напрямую, встраивание в постороннюю заметку) — лес.

**Кандидаты.** Для узла N типа T каждое правило `P: children: T: свойство` даёт кандидатов-родителей
типа P: цели ссылок в свойстве, заметки из `file.links`/`file.backlinks`. Корень без типа подходит
любому правилу.

**Основной родитель.** Лучший кандидат по порядку: более низкий уровень типа родителя → связь через
свойство важнее текстовой → порядок значения в списке → порядок родителя в сортировке Bases.

**Циклы.** Если основные связи образуют цикл, вершиной цикла становится узел, у которого больше
кандидатов-детей; при равенстве — раньше в сортировке Bases. У вершины выбирается следующий кандидат
вне её поддерева (или никакой). Разорванная связь, обратная к оставшейся, отображается стрелкой в обе
стороны; прочие — штрихом.

**Остальные связи.**

- кандидат — предок по основной цепочке → не рисуется;
- кандидат в графе и не предок → штриховая линия «ещё и здесь»;
- цель свойства вне графа нужного типа → подпись «ещё в: X»; если та же подпись есть у предка —
  не повторяется (унаследованная).

**Сироты.** Узлы без родителя при наличии корня показываются отдельной группой «Без родителя».

Порядок детей — порядок сортировки Bases.

## Действия: одно ядро

Каждое действие описывает желаемое дерево, из которого выводится план.

1. Изменение в памяти: создать узел под P / сменить родителя N на P / сменить тип N.
2. Пересчёт ссылок для узла и всех потомков сверху вниз:
   - свойство ребра получает родителя; старый основной родитель в этом свойстве заменяется на месте,
     штриховые значения остаются;
   - если старое ребро было в другом свойстве — старый родитель оттуда удаляется;
   - свойство из `inherit` = объединение по родителям-через-свойства: родитель сам, если его тип
     связывает детей этим свойством, иначе значение этого свойства у родителя;
   - для смены типа — рецепт типа.
3. Разница с текущим frontmatter = план: патчи, создания, дописывания, переносы файлов.
4. Проверка: план применяется к копии снимка, дерево строится заново тем же кодом. Требуется:
   у узла нужный родитель (и тип), у остальных родители не изменились, пара типов разрешена, нет
   цикла. Иначе действие отклоняется с причиной.
5. Применение (`processFrontMatter`, `vault.create`, `vault.process`, `fileManager.renameFile`) и
   запись транзакции в стек отмены.

Список или скаляр: сохраняется текущая форма значения; если ключа нет — как у других заметок
снимка; по умолчанию список. Ссылки пишутся как `"[[linktext]]"` через `fileToLinktext`.

**Отмена.** Транзакция хранит значения «до/после» затронутых ключей, созданные файлы с содержимым,
дописанные строки, переносы. Откат в обратном порядке; если текущее значение не совпадает с «после» —
этот шаг пропускается и пользователь предупреждается. Стек в памяти плагина до перезапуска; Cmd/Ctrl+Z
в фокусе вида, кнопка в уведомлении и в панели вида.

**Смена типа при неподходящих детях** — блокируется со списком. **Перенос в собственного потомка**
— недопустимая цель.

## Представления

Одна модель `Structure`, несколько отрисовщиков. Состояние (свёрнутые ветки, масштаб, прокрутка)
живёт в памяти по ключу «корень + имя вида» и переживает обновления данных.

- **graph** (по умолчанию) — дерево слева направо, как mermaid-flowchart из `view.js`: узлы HTML,
  связи SVG (кривые Безье со стрелками), штриховые дополнительные связи, стрелка в обе стороны,
  лёгкие рамки вокруг ветвей первого уровня, у которых есть дети. Масштаб Ctrl/Cmd+колесо и кнопки,
  прокрутка нативная, перетаскивание фона сдвигает, «вписать».
- **outline** — вложенный список со сворачиванием, тем же «+», перетаскиванием и подписями
  «ещё в/ещё под».

Идеи на потом (та же модель): колонки как в Finder (удобно для глубоких деревьев), радиальная карта
от корня, «сосульки»/treemap по числу потомков, доска «уровень = колонка», мини-карта ошибок схемы
(заметки с неразрешёнными ссылками и конфликтами типов).

Узел — обычная ссылка Obsidian: клик открывает, Mod+клик — в новой вкладке, наведение — превью;
`data-type`/`data-path` для внешнего оформления. «+» и меню узла: добавить ребёнка (типы из схемы,
недоступные — с причиной), сменить тип, переместить в…, открыть. После создания Enter — сосед того же
типа, Tab — ребёнок, Esc — выход.

## Архитектура кода

- `src/core/` — чистый TypeScript без `obsidian`: `schema` (разбор и проверка конфига), `typing`
  (опознание типа), `structure` (дерево), `planner` (действия → план → проверка), `undo` (модель
  транзакций), `layout` (раскладка графа).
- `src/obsidian/` — адаптеры: снимок из `metadataCache`, поиск корня, применение плана и отмена.
- `src/view/` — `StructureView` (BasesView), отрисовщики graph/outline, взаимодействия.
- `src/main.ts` — регистрация вида, команда отмены.

Core тестируется юнит-тестами на снимках, включая эталон, повторяющий правила `view.js` на данных
категории `knowledge base`; view — jsdom-тестами; итог — вручную через Obsidian CLI на демо-хранилищах
в `dev-vault-structure`: копия структуры `Base/Obsidian`, проекты → задачи, источники → задачи
по свойству, курс по папкам и `up`, карта контента со взаимными ссылками, оргструктура с
матричным подчинением.
